# Optimization bottlenecks and source audit

This note maps optimization-shaped problems to code that exists in the pinned AAH20 source snapshots and to ApexGraphSwarm's current local control/benchmark contracts. It is a design/evaluation guide, not evidence that one framework or kernel outperforms another. “NP-hard” describes a general mathematical formulation; it does not describe every workload instance, nor does a heuristic solve that formulation exactly.

The candidate methods below are Python routines in those repositories, not active pieces of ApexGraphSwarm's runtime. The ApexGraphSwarm runtime remains the allowlisted durable SQLite `ControlStore`; the harness runner is a separate opt-in process bridge. The benchmark in `scripts/benchmark_swarm.py` dispatches a deterministic zero-cost SHA-256 fixture through SQLite. It is not a model, graph-retrieval, provider-rate-limit, or visual-rendering benchmark.

## Bottleneck map

| Bottleneck | What the pinned code actually does | Correct interpretation and candidate use | Measurements needed |
|---|---|---|---|
| Durable admission and oversubscription | `apexgraphswarm/control.py::ControlStore` uses SQLite transactions, cost reservations, fenced leases, recovery, and reconciliation. `MAX_ACTIVE=64`, `MAX_AGENTS=300`. The benchmark's logical agent count does not itself create that many live workers. | Operational contention and backpressure, not an NP-hard optimization. Keep logical identities, active leases, provider requests, and external side effects as separate counts. The AAH20 schedulers are not drop-in replacements for the durable state machine. | Active lease trace; accepted/rejected work; queue and end-to-end p50/p95/p99; lease recovery; duplicate effects; provider throttles; reserved versus reconciled actual cost. |
| Resource-constrained scheduling | Agentic `SandboxResourceScheduler.solve` orders by lock contention/duration and assigns serial availability times to exclusive lock names. Graph-swarm `solve_disjunctive_tool_scheduling` performs topological ready-queue LPT using one tool-resource ID per task. MiroFish `DisjunctiveEventScheduler.solve` greedily assigns ready work to worker timelines. | General precedence/job-shop scheduling is combinatorial, but these are bounded polynomial heuristics. None is established as an optimal makespan solver. Validate DAGs, resource capacities, unknown IDs, and completeness; compare to exact optima on tiny fixtures. External provider quotas and I/O waits still require runtime feedback. | Makespan gap versus tiny exact optimum/lower bound; precedence/resource violations; utilization and queue time by resource; fairness/starvation; cyclic and burst inputs. |
| Tool/model selection under constraints | Agentic `CombinatorialToolRouter.solve` recursively explores include/exclude branches with prerequisite closure and an additive utility/latency/token objective. | Dependency-constrained multidimensional knapsack is NP-hard in general; branch-and-bound has exponential worst case. Utility is a declared proxy, not a learned success probability or a bill. Keep candidate sets small, test objective/closure against exhaustive tiny cases, and report timeouts/gap. | Nodes expanded and solve time by inventory size; exact small-instance gap; budget and prerequisite violations; predicted versus actual latency/token/cost; held-out success at matched budget. |
| Budgeted GraphRAG and memory retrieval | GraphRAG `SubmodularGraphSummarizer.solve` repeatedly selects feasible units by marginal coverage/salience per token and compares a best singleton. Agentic `SubmodularMemoryRetriever.solve` uses lazy-greedy topic coverage plus an embedding-distance term. Graph-swarm `solve_budgeted_attention_routing` sorts by entropy/token and applies each agent's focus/capacity independently. | Budgeted coverage is combinatorial in general. The implementations do not establish a universal approximation guarantee. The attention routine is not marginal submodular routing; it may duplicate evidence between agents. Internal diversity/entropy is not a substitute for relevance or answer support. | Recall@k/nDCG; citation support and answer correctness; token compliance; duplicate evidence; index build/update time; query latency and cost at matched quality. |
| Query-focused connected evidence | GraphRAG `PrizeCollectingSteinerTreeSolver.solve` chooses one root, expands by local edge-cost/node-prize tests, then removes negative-contribution leaves. | The general PCST formulation is NP-hard. This implementation is a greedy seed-rooted heuristic, not a source-verified primal-dual guarantee or global optimum. It can miss other components/routes; compare to shortest-path and exact small graph baselines. | Evidence recall; connectedness; prize-minus-cost gap on tiny exact instances; seed/disconnected/weight sensitivity; output tokens and latency. |
| Community partition / edge reduction | GraphRAG `HierarchicalCommunityDetector.solve` makes local modularity moves up to a pass bound; it does not implement multilevel Louvain coarsening. `SpectralGraphSparsifier.sparsify` builds a degree-limited high-weight forest, then adds high-weight edges; it does not compute effective resistance or a spectral approximation error. | These are polynomial heuristics despite NP-hard problem labels in adjacent kernel descriptions. Do not treat names/metrics as proof of spectral or globally optimal behavior. Keep unsparsified evidence reachable and gate adoption on task quality. | Preprocessing time/RSS; edge and component counts; degree constraints; cut/community stability; spectral error on small graphs; downstream retrieval/answer parity. |
| Coalition structure | MiroFish `OptimalCoalitionStructureSolver.solve` enumerates bitmask subsets and proper submasks with dynamic programming, using a synthetic `compute_coalition_value`. | This really is exponential subset/partition search (about O(3^n) partition transitions, O(2^n) DP/cache space, plus pairwise coalition-value work). It is suitable as a tiny-instance exact oracle, not a general 100/300-agent runtime strategy. Exactness is relative to its assumed utility function only. | Runtime/RSS by n; comparison gap for scalable methods on same tiny instances; sensitivity to utility weights; real task quality separately on held-out tasks. |
| Graph I/O, context, and display | The audited routines construct in-memory adjacency, sets, and candidate collections. Current benchmark fixture hashes small strings and does not load a graph. | Graph ingestion/indexing, serialization, context windows, provider networking, and browser drawing are operational/memory limits—not automatically NP-hard. Keep server evidence scope separate from UI sampling/LOD. | Cold ingest and query p50/p95/p99; peak RSS/index size/bytes; prompt tokens; measured browser timing on pinned hardware; full evidence versus sampled-view parity. |

## Guardrails before using a kernel

1. Treat these repositories as candidate baselines, not runtime claims. The presence of a class named “optimal,” “spectral,” “deadlock-free,” or “submodular” is not evidence that the property is proved or measured by the code.
2. Run tiny deterministic fixtures with known optima or invariants first. Include empty, disconnected, cyclic, duplicate-ID, invalid-resource, and budget-underflow cases where relevant.
3. For a fair “surpass” test, pin each candidate's source revision, inputs, model/provider, permissions, price evidence, retries, deadlines, and active-worker cap. Use equal-budget and equal-deadline comparisons; count failed attempts and rework.
4. Keep data quality and execution reliability separate: GraphRAG must be judged on held-out relevance and citation support; orchestration must be judged on correct transitions, safe recovery, queue time, and reconciled cost.
5. Do not extrapolate the 1/10/30/100/300 logical-agent fixture tiers to model concurrency or 100/300 active workers. The current control store permits at most 64 active leases in one DB, and only provider receipts can establish external usage/cost.

See `apps/web/lib/optimization-evidence.ts` for the structured, UI-consumable evidence records. The metrics listed there are proposed measurements; no superiority or production SLO is asserted by this source audit.
