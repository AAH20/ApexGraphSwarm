## What the source implements

**AgentIAM Lab.** `src/agentiam/fabric.py` models universal principals and scoped grants, evaluates principal/owner/tenant/purpose/resource/action, approval-count and risk conditions, recursively checks/revokes parent grants, and creates short-lived `PhysicalActionLease` objects. Its decision path attaches obligations for black-box recording and an independent safety controller. `src/agentiam/model.py` models task-token audience, resource, action and confirmation-key checks, cascading delegation revocation, and HMAC-SHA256 integrity receipts. `src/agentiam/conformance.py` contains nine deterministic scenarios for delegation, token checks, MCP-like audience checks, revocation, tenant/purpose isolation, approvals, and physical-action prerequisites. These are local fixtures and assertions, not calls to a real authorization server, protected MCP server, hardware trust source, or robot.

Published limits matter: the lab README identifies its token/HMAC receipt as shared-secret integrity, not public-key non-repudiation; asymmetric receipt signing/offline verification and cloud/workload identity adapters are roadmap items. Current principal and grant state is held in process dictionaries. The GitHub Action runs the portable core suite; cloud identity-provider adapters are described as future work.

The physical lease method requires an ALLOW decision bound to the request and policy revision, checks decision expiry, attestation/readiness/model fields, and caps lease life at 30 seconds. It returns an `evidence_digest` (plain SHA-256 over the lease body), not a signature. The schema itself says an independent safety controller remains mandatory. This is a useful lease contract and test seam; it does not authorize or actuate physical equipment.

**Agent JIT IAM / Aegis.** In `agentiam/authority.py`, `ProviderOperation` matches method, path and request facts; a capability binds subject, workload string, provider, operations, denies, expiry and max-use count. Canonical JSON plus HMAC-SHA256 signs capabilities and receipts. Explicit denied paths are checked before allow rules. `ReplayStore` uses SQLite transactions for max-use counters; this survives broker reconstruction only if the caller configures a persistent `replay_db` path. The tests exercise these local paths, including replay persistence with a temporary SQLite file. The new API is an authorization decision component: the README says an external trusted proxy must forward only after ALLOW and add provider credentials outside the agent.

The old `AgentJITDelegator` API remains exported for compatibility. It has string-scope tokens, a process-local consumed-token set, a local environment/file kill switch, and a SHA-256-linked ledger. The ledger hash chain is not a signature and the in-memory consumed-token set does not provide distributed replay protection.

## Gaps that block production IAM/PAM use

| Control | AgentIAM Lab | Agent JIT IAM | Required before Apex connects it to enterprise authority |
|---|---|---|---|
| **JIT lifetime** | Grant API bounds delegation lifetime to 1–3600 seconds; token/lease examples use shorter bounds. Decision/lease are local objects. | New broker requires positive root TTL, but does not cap it; child expiry may not exceed parent. Legacy token API has separate clamping behavior. | Enforce a server-side maximum root lifetime, clock-skew rules, task ID, audience, resource and action on every issued credential; expiry must be enforced by the resource or gateway too. |
| **Approval** | Policy compares `len(approvals)` to `required_approvals`; inspected schema/model do not establish distinct approver identities, signed approval evidence, or durable approval state. | No approval workflow or approval-verification API in the pinned broker. | Bind each approval to named reviewer identity, tenant, exact requested scope, task, policy version and expiry; verify it at enforcement time and store an immutable decision record. |
| **Revocation** | `TrustFabric.revoke` recursively marks parent and descendants; local `_active_grant` sees it. This is in-memory lab behavior. | No revoke API or revocation registry exists in the newer `AuthorityBroker`; `parent_digest` is included in the capability but is not resolved during `authorize`. | Add a durable, low-latency revocation authority and check it online at each sensitive action; define cache bounds, descendant revocation, fail-closed behavior, and tested recovery during IAM outages. |
| **Delegation narrowing** | Resources/actions/purpose/depth and required-approval count are narrowed. The `remaining_budget` field is not consumed/reserved in the decision flow; geographic and data-classification fields are not checked by `evaluate`. | `_validate_delegation` checks provider, expiry, max uses, and method/path. It does not ensure the child subject/workload is bound to the parent, or narrow child operation constraints and denied paths. `authorize` does not walk/check the parent chain. | Test non-amplification over every claim and enforcement path; bind parent/child principal, workload, tenant, purpose, policy, budget, constraints, denies and maximum delegation depth. |
| **Receipts** | Receipt model explicitly marks HMAC as lab-only and `non_repudiation: false`. Physical lease digest is unsigned. Receipt schema decision label `ALLOW_WITH_APPROVAL` differs from the model enum `REQUIRE_APPROVAL`; define the mapping before interop. | Broker receipt uses HMAC and a per-instance chain head; default SQLite replay and receipt-chain head are in-memory. It cannot attest that a real external effect happened because the broker makes no provider call. | Separate authorization decision from execution evidence. Persist receipts, include issuer/key identity and policy version, support independent verification/key rotation, and reconcile provider outcome/usage with the exact authorized request. |
| **MCP** | A local token test checks audience/resource/action; it does not implement MCP transport, resource-server authentication, or a protected MCP tool server. | Generic HTTP operation policy; no MCP protocol adapter in the tree. | Enforce at the MCP server/tool boundary with server-selected endpoint identity, audience and resource indicators. Treat tool descriptions/agent intent as untrusted; a broker ALLOW must gate the actual request. |
| **Physical/IoT** | Schemas and fixture require device attestation, safety `READY`, model digest, black-box record, an independent safety controller, and short lease. None is connected to physical equipment. | No device, robot, industrial-control, or IoT adapter. | Require trusted hardware/workload attestation, independent safety PLC/controller, bounded action allowlist, emergency stop, sensor freshness, state revalidation at actuation, human approval by risk class, and signed actuation/result evidence. Never equate model confidence or a valid lease with physical safety. |

For the newer JIT broker there are additional implementation risks to close before production: `subject` is signed but not an `authorize` input, so the caller identity is not checked there; the broker trusts the supplied workload value, so the proxy must derive it from a verified workload identity rather than an agent header; root TTL has no configured upper bound; and `max_uses` is a count, not a money or impact budget. HMAC provides integrity to holders of the shared secret, not public verification or non-repudiation. The test suite does not exercise parent revocation because the new capability type has no revocation mechanism.

## Apex specialist team and integration boundary

Use these as **analysis and evidence-producing specialists**, not as privileged executors:

- **Identity/delegation specialist:** compare agent, accountable principal, tenant, purpose and delegation chain against the Apex task record; cite the exact policy/schema revision.
- **MCP enforcement specialist:** check the target server’s audience/resource/action and whether the authorization decision actually gates tool dispatch. It may report missing enforcement but cannot self-approve it.
- **JIT/PAM specialist:** propose minimum provider operations and lifetime, identify approval requirements, and reconcile issued/revoked/expired state with the external IAM/PAM receipt.
- **Physical-action safety specialist:** review device attestation, safety state, independent controller, action allowlist and actuation evidence; remain a hard deny without those external checks.

Apex should own task admission, tenant scope, task-to-agent identity binding, durable events, and cost/impact reservation. A separate server-side adapter should request narrowly scoped grants from the selected real IAM/PAM provider, keep secrets out of agent prompts and browser state, and pass only opaque, expiring handles to a trusted proxy. The proxy must derive workload identity from the runtime, enforce each tool/API call, and return a correlated outcome receipt. These repositories currently supply useful contract/test inputs, not that end-to-end enterprise execution path.

For a private data center or PhysicalAI/IoT deployment, the first production gate is a synthetic integration against the actual selected IdP/PAM, secrets manager, MCP gateway and safety controller. Require adversarial tests for cross-tenant use, forged/expired/revoked capabilities, parent-chain revocation, approvals, duplicate/replayed actions, proxy loss, broker loss, clock drift and stale device state. Production enablement should stay disabled until the system proves scoped grant, denial, cancellation/revocation, durable receipt verification, and safe physical stop/recovery without contacting real equipment during the lab phase.
