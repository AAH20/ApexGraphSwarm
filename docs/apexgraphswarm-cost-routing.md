# ApexGraphSwarm cost ledger and routing design

**Checked 2026-09-27.** This design separates a routing plan from execution, provider usage, and an invoice. Model prices and product entitlements change; every rate and benchmark must carry its source and observation time. A missing value is **unknown**, never zero. This document is an accounting and admission-control design, not a provider recommendation.

## Catalog and candidate eligibility

Keep harness, model, provider, and transport identities separate. The current harness catalog names Codex, Claude Code, Cursor, Antigravity, OpenCode, and Hermes; it describes authentication/billing paths but does not prove that a given account is entitled to arbitrary programmatic calls. Model IDs are independently registered with provider, exact API ID, endpoint, modality, context limit, tool/structured-output support, privacy/data-retention and region attributes, rate-card source, and checked timestamp. Add user-defined model/API IDs as records; never synthesize a universal “GPT-6” or harness price from a product name. Models named in the planning UI (GPT-6 Astra/Sol/Luna, GPT-5.6 Sol/Terra/Luna, GPT-5.5, and GPT-Daybreak Blue) remain unpriced until their particular execution route has a verified rate card. A ChatGPT/Codex plan allowance is not an API token rate.

For OpenRouter, refresh the public model catalog and preserve the exact returned model ID and pricing fields; its catalog exposes context, modalities, model properties and pricing, but the record is a time-stamped quote, not a bill. For vLLM, model rates are not provider token charges: collect the configured host/GPU price, billed GPU count and time, storage/network/operations allocation, and a declared allocation rule across workloads. Do not interpret vLLM KV-cache occupancy as GPU compute utilization. A candidate is eligible only if it passes hard requirements (capability, context, privacy, region, allowed auth path, spending cap); rank eligible candidates using measured task-specific quality, observed latency, and estimated total cost with explicit weights. Benchmark scores need dataset, date, sample count, harness/model/provider route, and uncertainty. If no candidate has sufficient evidence, return “no evidence-based recommendation” with blockers rather than a fabricated winner.

## Cost ledger and lifecycle

Record one append-only ledger row per model request, agent, retry, tool, and hosting interval. Minimum dimensions: workspace/run/parent ID; task class and prompt/schema version; agent role/fanout/retry/step; requested model/provider versus resolved model/provider/service tier; route and rate-card revision; start/end/status/cancel; usage source and idempotent provider generation/request ID; input, cache-read, cache-write, output, and reasoning usage; tool name/count/charge; GPU billed time, device count, measured utilization and allocation method; currency; and estimate, reservation, actual usage, and invoiced amounts as separate values. Keep credentials and prompt content out of this cost record unless a separate, access-controlled audit store requires them.

1. **Plan estimate.** Calculate from editable assumptions: uncached input, cache reads/writes, output, model-call count, tool calls, retries, fanout, expected success rate, fixed-cost allocation, and local hosting. Output tokens already include reasoning tokens where the provider defines reasoning as a subset; do not add reasoning a second time. Report estimate range/unknown fields, rate provenance, assumptions, and whether the execution model is different from the cost model.
2. **Admission reservation.** Before dispatch, reserve a conservative upper bound derived from maximum agent calls/steps, output caps, retry policy, tool caps, fallback routes, and maximum GPU wall time. Reserve atomically against per-run, workspace, and monthly limits. Deny or require an explicit cap/override when a paid route has unknown rates. Unknown subscription quota consumption is not free capacity. Release only the unused remainder after calls are reconciled; retain charges for failed and cancelled calls that incurred usage.
3. **Actual usage.** Persist provider response usage for each request and reconcile later by generation ID when available. OpenRouter exposes routed model/provider, service tier, cache information, latency, cancellation and total-cost metadata through its generation endpoint. Include search/tool charges separately from model tokens. Do not infer a zero charge from an empty response or failed job.
4. **Invoice reconciliation.** Provider billing/cost exports, credits, taxes, plan charges and adjustments form a separate finance record. Usage counters and response-level costs are operational actuals, not necessarily the invoice total. Reconcile at provider account/workspace and billing period, retain the delta and its reason, and never label a projection “invoiced.” Subscription products report plan/credit/quota usage and fixed plan allocation separately from hypothetical per-token spend.

OpenRouter pricing metadata is dynamic and route-dependent; direct providers, service tiers, context thresholds, modalities, discounts, BYOK arrangements, cached input and cache writes can all alter effective rates. Use the actual routed provider and actual tier when reconciling. Anthropic cache writes can have a premium and reads a discount; OpenAI/Grok caching follows different rules. A shared system prefix across ApexGraphSwarm specialists can reduce input costs only when that provider/model cache recognizes the exact prefix within its cache lifetime. Simultaneous misses may all be billed before a cache is populated. Record cache-read and cache-write counts per request, not an assumed shared-prefix discount.

Tool loops add their own cost surface: tool-result tokens become model input on later turns; web search or browser/API tools may charge by invocation; local code tools consume CPU/GPU/network and wall time even with no model-token charge. Fanout cost is the **sum** of specialist and critic attempts. Parallel fanout can lower elapsed latency but does not divide total usage. The critic receives earlier outputs, so its prompt size should be measured independently. Count retries, fallback model calls, partial/cancelled calls, and their tools in the run total.

For shared vLLM, report both workload-attributed compute and host-billed capacity. The default estimate is `GPU hourly rate × billed GPU-hours × GPU count + explicitly allocated storage/network/operations`. When forecasting a utilization-adjusted unit cost, document whether utilization increases required provisioned hours; do not divide already-billed wall time by utilization twice. Use vLLM token, request, cache, and latency metrics with GPU telemetry (for example DCGM GPU utilization), and state the allocation rule used for multi-tenant GPU cost.

## Unit economics and sample

For a stable workload with started-run success probability `p > 0`, expected variable cost per successful run is `expected variable cost per started run / p`. Add allocated monthly fixed cost per expected success, or equivalently compute monthly all-in cost divided by expected successful runs. A run with `p = 0` has unknown/infinite cost per success. Monthly expected contribution is `expected successful runs × revenue per success − variable spend − allocated fixed spend`; failed runs still incur cost. Break-even is defined only when expected contribution per started run is positive. Report the denominator and observation window for success rate; do not silently interpret a benchmark pass rate as production success probability.

**Hypothetical illustration only (USD; not a current quote or invoice).** Assume three Claude Opus 4.6 calls per ApexGraphSwarm run (two specialists plus critic), with one specialist retry: four calls total. Each call is assumed to use 12,000 uncached input tokens at $5/M, 3,000 cache-read tokens at $0.50/M, 500 cache-write tokens at $6.25/M, and 2,000 output tokens at $25/M. This yields `$0.114625` per call and `$0.4585` per started run, assuming every call has the same usage and rate. At 500 starts/month, 85% success, $20 allocated fixed spend/month, and $1.25 revenue per success: variable spend is `$229.25`, expected successes are `425`, total spend `$249.25`, cost per success about `$0.5865`, and expected contribution about `$282.00/month`. These figures exclude tools, taxes, cache misses, route/tier changes and usage variance. The source rate card is the OpenRouter public catalog sampled on 2026-09-27; re-fetch and verify the exact model/route before use. If cache-write pricing is absent or any rate is unknown, the calculator must show the dependent total as unknown rather than reuse this example.

## Planning interface and exported plan

The delegation planner should produce a versioned JSON **plan**: task class, requirements, privacy constraints, eligible candidates and exclusion reasons, benchmark provenance, requested routes, editable rates and timestamps, token/tool/GPU/retry/fanout caps, estimated range, budget decision, and rationale. Include `executionStatus: "planned"`, `actualUsage: null`, and `invoiceStatus: "not-reconciled"`; export no secrets. Execution requires a separate user action and server-side capability/auth/budget validation. Updating a rate or model registry invalidates a prior estimate and requires a fresh plan/reservation. A selected candidate means only “best under these stated constraints and measurements,” never universally best.
