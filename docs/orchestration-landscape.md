# Orchestration landscape

**Evidence reviewed:** 2026-09-27. This is a capability and integration comparison, not a leaderboard. “Agent count” is not a common workload definition: registered logical agents, delegated tasks, queued work, active workers, and simultaneous model requests measure different things. No capacity claim is inferred from a framework’s product description.

## The layers answer different questions

| System | Primary layer and job | Delegation / workflow | Durability and accounting | Retrieval fit |
|---|---|---|---|---|
| **LangChain + LangGraph + Deep Agents** | Framework components, stateful graph runtime, and higher-level agent harness. LangGraph explicitly targets controllable stateful execution; Deep Agents adds planning/filesystem context, tools, skills, subagents, and human steering. [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) · [Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview) | Deterministic graph transitions and model-driven choices can be combined. Deep Agents supports sync/async subagent delegation; asynchronous subagents require an Agent Protocol server and task lifecycle handling. [Subagents](https://docs.langchain.com/oss/python/deepagents/subagents) · [Async subagents](https://docs.langchain.com/oss/python/deepagents/async-subagents) | Checkpointers preserve graph state and stores share cross-thread data. In-memory state does not survive restart; persistent backends and retention must be selected. Replaying a checkpoint does not make external side effects exactly once. There is no universal cross-agent budget ledger in these layers. [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | Modular loaders, splitters, embeddings, vector stores, retrievers, and fixed or agentic RAG patterns. Apex must still add graph snapshot scoping, node citations, access checks, and freshness. [Deep Agents retrieval](https://docs.langchain.com/oss/python/deepagents/retrieval) |
| **CrewAI** | Agent framework with role/task “Crews” and event-driven “Flows.” A manager agent is an execution pattern, not a general scheduler or proof of reasoning quality. [Crews](https://docs.crewai.com/en/concepts/crews) | Sequential/hierarchical Crews; Flows coordinate deterministic events/state and can invoke Crews for open-ended tasks. [Flows](https://docs.crewai.com/en/concepts/flows) | Flow persistence documents SQLite-backed save/resume/fork. This does not itself provide globally enforced budgets or exactly-once external effects. Cost and concurrency need app/provider controls. | First-party Knowledge and Memory APIs include vector/retrieval integrations and semantic, recency, and importance recall. An Apex graph ingestion/provenance adapter remains separate. [Knowledge](https://docs.crewai.com/en/concepts/knowledge) · [Memory](https://docs.crewai.com/en/concepts/memory) |
| **Microsoft Agent Framework** | Agent abstraction plus typed dataflow workflow runtime; supports sequential, concurrent, handoff, group chat, and Magentic manager orchestration. It is a runtime, not a company/task control plane. [Orchestrations](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/) | Explicit workflow edges support parallel execution, requests for human input, and agent handoffs. | Checkpointing is opt-in and needs a `CheckpointManager`; restore requires the original topology and executor identities. Conversation storage may be local, service-managed, or custom. Neither option guarantees exactly-once tool side effects or supplies a shared cross-provider budget ledger. [Checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints) · [Storage](https://learn.microsoft.com/en-us/agent-framework/agents/conversations/storage) | The docs list RAG and provider packages; Apex still needs its own permission-aware graph retrieval and stable evidence links. [Capabilities](https://learn.microsoft.com/en-us/agent-framework/) |
| **Google ADK** | Multi-language agent framework and graph workflow runtime. ADK 2.0 graph nodes combine code/tools/model agents, with explicit routes; sequential, parallel, loop, and dynamic workflows are also documented. [Graph workflows](https://adk.dev/graphs/) | Workflow graphs can route structured data through deterministic and agent nodes; ADK also documents managed agents and run resume/cancel capabilities. | Session and memory persistence are service choices. In-memory session and memory stores are for development and lose state on restart; managed/persistent services are available. ADK does not constitute Apex’s tenant admission and cost-reconciliation ledger. [Context services](https://adk.dev/sessions/) | First-party `MemoryService` supports ingestion and search; Python options include in-memory memory, Vertex AI Memory Bank, and Vertex AI RAG Memory. Snapshot identity, node citations, and access policy still belong in an Apex adapter. [Memory](https://adk.dev/sessions/memory/) |
| **Paperclip** | Business-oriented agent operations/control plane: organizations, goals, issues, assignments, heartbeats, workspaces, approvals, usage reports, and adapter dispatch. Agent execution is performed by external adapters. [Core concepts](https://github.com/paperclipai/paperclip/blob/master/docs/start/core-concepts.md) | CEO/manager-style agents may decompose goals into tasks; issues are assigned and checked out for execution. This is organizational task management, not a swarm-search optimizer or multi-agent answer-quality proof. | The documented budget surface aggregates adapter-reported usage and supports alert/pause policies. Actual cost correctness depends on adapter reporting and reconciliation. The repository spec places a dedicated knowledge base outside the core; use an external retrieval/plugin surface. [Budgets](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/costs-and-budgets.md) · [Spec](https://github.com/paperclipai/paperclip/blob/master/doc/SPEC.md) | Organization goals, issue history, comments, and artifacts provide operational context; a separate permission-aware retrieval service is needed for repository/enterprise knowledge. |
| **Google Agent Executor (AX)** | Distributed task/workspace/model executor over Agent Substrate; lower-level than an agent reasoning framework or business control plane. [Local assessment](google-ax-assessment.md) | Declarative task/workspace provisioning and lifecycle. Public contract reviewed does not provide a complete one-shot submit → result → verified terminal-state interface by itself. | Capacity and terminal semantics need verification for a pinned private deployment. A child process exit is not automatically an AX task’s successful terminal result; there is no public reproducible 150,000-concurrent-agent benchmark in the reviewed release. [AX source](https://github.com/google/ax) | MCP/skills may be configured in workspaces, but AX does not ingest Apex graph snapshots or define evidence authorization/citations. |

**Paperclip is not interchangeable with the other rows.** Its value is operational management across external runtimes. Pairing two control planes requires one explicit authority for task claims, cancellation, tenant isolation, and cost settlement; otherwise duplicate assignment and ambiguous spend become system-level risks.

No numeric score is quoted here unless its model/version, task, metric, and date can be checked. This review did not call a paid API or execute an upstream benchmark.

## Practical fit for ApexGraphSwarm

Apex already has a local durable SQLite control plane for run/task records, leases, events, retries, and budget reservation/reconciliation. Treat that as the admission and accounting authority while evaluating a framework behind a fixed adapter. A framework may own its internal graph/checkpoints or retrieval, but adapter acceptance must bind the framework run to an Apex run/task ID, snapshot identity, evidence references, cancellation result, and usage/cost state. Uncertain paid attempts must stay in reconciliation; framework retry behavior alone cannot resolve an unknown external charge.

Choose based on the workload and boundary you need:

- **Explicit typed graph with durable checkpoints:** test LangGraph or Microsoft Agent Framework.
- **Agent harness with filesystem context and delegation:** test Deep Agents.
- **Role/task Crews plus event-driven application flow:** test CrewAI.
- **Graph routes, Google deployment, and managed memory choices:** test ADK.
- **Company/org/task operations across multiple external executors:** evaluate Paperclip as a control plane, with a single scheduler owner.
- **Separate execution placement from control and reasoning:** treat AX as an executor only after its result, identity, cancellation, and resource-accounting contracts are proven.

A meaningful local comparison should pin source versions and model IDs, use a held-out task suite with ground-truth success checks, fix retrieval/tools/sandbox/prompt/output limits, and record wall time, active worker concurrency, model requests, input/output usage, known and unknown cost, retries, and evidence citation precision. Report deterministic scheduler fixtures separately from live model runs. Do not market logical roster size as model-call concurrency.
